# Wally 테스트 시나리오 구현 검토 결과

- 기준 문서: `docs/ref/2_test_scenarios.md`
- 검토 대상: 현재 `src` 및 Android 프로젝트
- 검토 방식: 정적 코드 검토와 빌드 결과 기준
- 상태 의미
  - **구현됨**: 시나리오를 수행할 코드 경로가 확인됨
  - **일부 구현**: 핵심 일부는 있으나 문서의 기대 동작을 모두 충족하지 않음
  - **미구현**: 해당 흐름 또는 필수 처리가 없음
  - **검증 필요**: 코드만으로 최종 결과를 확정할 수 있어 백엔드·카메라·실기 테스트가 필요함

> `구현됨`은 코드 구현 여부에 대한 판정이다. 실제 babycat 백엔드와 카메라를 연결한 통합 테스트 성공을 뜻하지는 않는다.

## A. 서버 인증과 로그인

### A-01: 일부 구현

서버 주소는 `wally_host`라는 키로 `localStorage`에 저장되고 이후 API 주소에 사용된다. 그러나 현재의 `authenticateServer()`는 입력값을 저장하기만 하고 실제 서버에 요청해 도달 가능 여부를 확인하지 않는다. 또한 서버 인증 여부는 `sessionStorage`에만 저장되므로 브라우저를 완전히 닫았다 다시 열면 주소가 남아 있어도 서버 주소 화면을 다시 거칠 수 있다.

구현 방향: 서버 주소 저장 전에 `/api`의 상태 확인용 엔드포인트 또는 로그인 엔드포인트에 제한 시간 요청을 보내야 한다. 응답 성공 시에만 주소와 인증 상태를 저장하고 로그인 화면으로 이동하며, 실패 시 입력 화면을 유지하고 `서버에 연결할 수 없습니다.`를 표시해야 한다. 저장된 주소가 있으면 앱 시작 시 같은 연결 검사를 수행해 성공할 때 로그인 화면으로 바로 이동하도록 구성하는 편이 적절하다.

### A-02: 구현됨

`useAuth.login()`이 `/api/login`에 아이디, 비밀번호, 로그인 유지 값을 전송한다. 401·403은 잘못된 자격증명으로 처리하고 로그인 화면에 `아이디 또는 비밀번호를 확인해주세요.`를 표시한다. 성공하면 세션을 저장하고 홈으로 이동한다. 네트워크 요청에는 5초 제한도 적용되어 있다.

실제 응답 필드가 babycat 계약과 맞는지는 통합 검증이 필요하다.

### A-03: 구현됨

로그인 코드가 HTTP 429를 전용 `LoginRateLimitError`로 구분해 로그인을 중단한다. 응답 본문의 `retry_after_seconds`, `retry_after`, `lockout_seconds`, `remaining_seconds`와 `Retry-After` 헤더의 초 또는 HTTP 날짜 형식을 지원한다. 남은 시간이 있으면 `30분 후 다시 시도해주세요.`처럼 표시하고, 시간이 없으면 `로그인 시도가 너무 많습니다. 잠시 후 다시 시도해주세요.`를 표시한다. 일반 아이디·비밀번호 오류 문구와 잠금 안내가 분리되어 있다.

웹·Android APK 빌드와 실기 덮어설치는 완료했다. 실제 계정을 10회 실패시켜 잠그는 검증은 30분 잠금 부작용을 피하기 위해 수행하지 않았다.

### A-04: 미구현

최초 로그인 응답의 강제 비밀번호 변경 플래그를 읽는 코드가 없고, 로그인 성공 시 항상 홈으로 이동한다. 설정 화면의 비밀번호 변경 시트를 자동으로 여는 상태와 새로고침 후 복원하는 처리도 없다.

구현 방향: 로그인·토큰 갱신 응답에서 `must_change_password`에 해당하는 서버 필드를 저장한다. 라우터 가드에서 이 값이 참이면 설정 경로 외 접근을 차단하고 비밀번호 변경 시트를 강제로 열어야 한다. 새로고침 시에도 서버의 사용자/세션 정보 또는 저장된 강제 변경 상태를 확인해 동일 화면을 복원해야 한다.

### A-05: 구현됨

현재 비밀번호와 새 비밀번호를 `/api/change-password`로 보내며 입력값 유효성을 검사한다. 변경 성공 시 비밀번호 변경 화면을 닫고 로컬 액세스·리프레시 토큰을 모두 삭제한 뒤, 서버 주소 화면을 거치지 않고 로그인 화면으로 이동한다. 로그인 버튼 아래의 기존 오류 문구 영역과 같은 위치·크기·색상으로 `비밀번호가 변경되었습니다. 새 비밀번호로 로그인해주세요.`를 한 번 표시한다. 일반 로그아웃과 구분하기 위해 일회성 로그인 안내가 있는 경우 라우터가 로그인 화면을 우선한다.

웹·Android APK 빌드와 실기 덮어설치는 완료했다. 실제 비밀번호 변경은 계정 자격증명과 다른 클라이언트의 세션에 영향을 주므로 자동 실행하지 않았다. 서버가 다른 기기를 포함한 전 세션을 폐기하는지는 백엔드 통합 테스트로 확인해야 한다.

### A-06: 구현됨

로그인 유지를 켜면 토큰과 리프레시 토큰을 `localStorage`에 저장한다. 인증 요청에서 401이 발생하면 리프레시 토큰으로 갱신한 뒤 원래 요청을 한 번 다시 수행한다. 앱을 다시 열었을 때 만료된 영구 세션은 백그라운드 갱신을 시작하고 임시 네트워크 장애만으로 저장 세션을 지우지 않는다.

10분 만료 후 갱신 및 브라우저 재시작은 실제 백엔드 토큰으로 검증해야 한다.

### A-07: 구현됨

로그인 유지를 끄면 세션을 `sessionStorage`에 저장한다. 만료된 비영구 세션은 초기화 과정에서 제거되며, 인증 요청이 401이면 갱신하지 않고 로그아웃한다. 탭 세션 종료 시 저장값도 사라지는 구조다.

실제 만료 시간 경과 테스트는 백엔드와 함께 검증해야 한다.

### A-08: 구현됨

다른 클라이언트 로그인으로 기존 토큰이 무효화되어 인증 요청이 401을 받으면, 비영구 세션은 즉시 로그아웃한다. 영구 세션은 갱신을 시도하고 갱신 토큰까지 거부되면 세션을 제거한다. 별도 세션 대체 안내 문구는 구현되어 있지 않아 문서에 적힌 알려진 공백과 일치한다.

### A-09: 구현됨

설정의 로그아웃 버튼은 로컬 액세스·리프레시 토큰을 즉시 삭제하고 서버 로그아웃 요청을 최선 노력 방식으로 전송한다. 저장된 서버 주소와 현재 서버 인증 상태는 유지하므로 일반 로그아웃 후 서버 주소 화면을 거치지 않고 로그인 화면으로 이동한다. 라우터 감시가 인증 화면 밖의 접근을 막기 때문에 브라우저 또는 Android 뒤로가기로 홈을 복원할 수 없다. 서버 인증 상태가 없는 완전한 새 세션에서만 서버 주소 화면을 사용한다.

로그인 버튼 아래에는 밑줄 없이 보조 색상으로 표시되는 `서버 주소 변경` 버튼이 있다. 이 버튼을 누르면 사용자 로그인 토큰, 저장된 서버 주소와 서버 인증 상태를 초기화하고 서버 주소 입력 화면으로 이동한다. Android 시스템 뒤로가기와는 분리되어 일반 로그아웃 동작에는 영향을 주지 않는다.

웹·Android APK 빌드와 실기 덮어설치는 완료했다. 실제 로그아웃 버튼 실행은 현재 기기의 저장 세션을 폐기하므로 자동 수행하지 않았다.

## B. 라이브 스트리밍과 수명주기

### A-10: 구현됨

카메라 이름·계정·비밀번호·IP·RTSP 포트·ONVIF 포트·스트림 경로를 `/camera`에 저장한다. 화면 재진입 시 서버 설정을 다시 조회하며 비밀번호 필드는 비우고 `password_set` 상태만 유지한다. 성공했을 때만 시트를 닫는다.

실제 babycat 필드명과 저장 결과는 실기 검증이 필요하다.

### A-11: 일부 구현

홈 진입 시 카메라 설정을 자동 조회하고 HLS 또는 WebRTC 재생을 자동으로 시도한다. 재생 실패 시 제한된 자동 재시도도 수행한다. 그러나 백엔드의 스트리밍 상태를 조회하고 정지 상태일 때 시작 명령을 보내는 로직은 없다. 즉, 이미 제공되는 스트림에 자동 연결하는 기능만 있고 문서의 `꺼져 있으면 자동으로 켠다`는 수명주기 제어는 구현되어 있지 않다.

구현 방향: 백엔드 스트리밍 상태 엔드포인트와 시작 엔드포인트를 추가해 상태가 정지일 때 시작 요청을 보낸다. 시작 시도는 전역으로 마지막 시각을 기록해 15초 쿨다운을 보장하고, 준비될 때까지 상태 조회와 재생 연결을 이어가야 한다.

### A-12: 미구현

SSE에서 `vlm_state`, `pipeline_state`, `infer_raw` 등의 상태를 수신하는 구조는 있지만, VLM 준비 완료를 기다려 분석 시작 명령을 보내는 코드가 없다. 홈에도 실시간 장면 설명을 표시하는 UI가 연결되어 있지 않다.

구현 방향: SSE 또는 상태 API에서 VLM `ready`와 분석 상태를 확인하고, 분석이 정지된 경우 15초 쿨다운을 적용해 시작 요청을 보낸다. `infer_raw`를 홈 상태 영역에 표시하고 오래된 판정에는 만료 상태를 적용해야 한다.

### A-13: 일부 구현

HLS 선택 UI와 `hls.js/light` 기반 재생, 네이티브 HLS 대체 경로가 구현되어 있다. 다만 현재 HLS URL은 `http://<host>:8888/live/index.m3u8`이고 인증 토큰이나 Authorization 헤더를 전달하지 않는다. 따라서 문서의 `앱에서는 인증 재생, 직접 주소는 401` 계약은 현재 코드로 충족하지 못한다.

구현 방향: babycat이 제공하는 인증 프록시 URL을 사용하거나, HLS 요청 전체에 인증 헤더를 넣을 수 있는 로더를 구성한다. 매니페스트뿐 아니라 세그먼트 요청에도 인증이 적용되어야 한다.

### A-14: 구현됨

HLS/WebRTC 전환 UI가 있고 선택값을 저장한다. WebRTC는 WHEP 연결을 수행하며 15초 동안 재시도한다. 최종 실패하면 `fallbackToHls()`가 HLS로 자동 전환한다. 전환 시 기존 HLS·WebRTC 자원을 정리하고 영상 요소를 다시 연결한다.

실제 UDP 8189 경로, 지연 시간, 화면 깜빡임 여부는 네트워크 실기 검증이 필요하다.

### A-15: 미구현

외부에서 스트리밍 또는 분석을 정지했을 때 백엔드 상태를 감시해 다시 시작하는 제어가 없다. 재생 요소의 멈춤을 감지해 동일 URL에 재접속하는 기능은 있지만 서버 수명주기를 다시 켜지는 못한다.

구현 방향: A-11·A-12의 상태 감시와 조건부 자동 시작을 공용 수명주기 composable로 구현하고 스트리밍·분석 각각에 15초 시작 쿨다운을 적용한다.

### A-16: 구현됨

방향 패드의 pointer down에서 `/ptz`로 이동 명령을 보내고 pointer up, leave, cancel에서 정지 명령을 보낸다. 상하좌우 외에 위치 저장과 복귀 명령도 구현되어 있다.

ONVIF 카메라의 축 방향과 정지 응답은 실기 검증이 필요하다.

### A-17: 구현됨

HLS는 재생 정지 상태를 8초마다 확인하고 15초 연결 제한 시간 안에서 최대 3회 빠르게 재시도한다. WebRTC도 연결 실패·끊김 시 재연결하며, 제한 시간 안에 연결되지 않으면 기존 정책대로 HLS로 전환한다.

빠른 재시도가 끝난 뒤에도 홈 화면이 보이고 카메라 주소가 존재하면 5초, 10초, 15초, 이후 최대 30초 간격으로 재연결을 계속한다. 영상 재생에 성공하면 장기 복구 횟수와 타이머를 초기화한다. 앱이 숨겨지거나 화면을 벗어날 때는 타이머를 정리하고, 앱이 다시 보이면 즉시 새 연결을 시작하므로 중복 재연결 루프가 남지 않는다.

웹·Android APK 빌드와 실기 덮어설치를 완료했다. 앱 실행 및 WebRTC 스트림 연결 로그를 확인했으며 치명적 실행 오류는 없었다. 실제 카메라 전원 또는 스트리밍 서버를 장시간 중단했다가 복구하는 최종 검증은 사용자 실기 확인이 필요하다.

## C. 이벤트와 기록

### A-18: 구현됨

인증 토큰을 포함한 SSE `/events` 연결, 키워드 일치 검사, 이벤트 버전 갱신, 알람 목록 새로고침, Android 이상행동 알림 생성이 구현되어 있다. `event_triggered`, `trigger_keywords`, `infer_raw`, `clip_count`를 이용해 중복 이벤트도 억제한다.

실제 SSE payload가 이 필드 구조를 사용하는지와 이벤트 지연은 통합 검증이 필요하다.

### A-19: 구현됨

기록 목록은 `/clips`에서 조회하며 선택 날짜를 `date_from`과 `date_to`로 전송한다. 응답을 앱에서도 다시 날짜로 필터링하고 날짜 변경 시 강제 재조회한다. 빈 목록과 오류 상태도 구분한다.

### A-20: 일부 구현

기록의 비디오 클립 자동 재생과 확대 재생은 구현되어 있고 클립 URL에는 토큰 쿼리를 붙인다. 그러나 `<video>`에 기본 `controls`가 없고 별도 탐색 바도 구현되어 있지 않아 문서에서 요구하는 시크 조작은 현재 할 수 없다. 또한 토큰이 URL에 노출되는 방식이며, 직접 주소 접근이 반드시 거부되는지는 백엔드의 토큰 검증에 달려 있다.

구현 방향: 기본 비디오 컨트롤 또는 앱 디자인에 맞는 재생·탐색 바를 추가한다. 가능한 경우 짧은 수명의 서명 URL 또는 Authorization 기반 미디어 요청으로 전환하고 직접 URL·만료 토큰·다른 세션 토큰 접근을 백엔드 통합 테스트로 확인한다.

### A-21: 구현됨

이벤트의 `clip_count`를 기준으로 최대 120초 동안 2초 간격으로 클립 목록을 조회해 감지에 대응하는 클립을 찾는다. 클립이 생성되면 기록 링크와 알림 이미지를 갱신한다.

실제 클립 순서와 `clip_count` 대응 규칙이 백엔드 계약과 일치하는지는 통합 검증이 필요하다.

## D. 회귀 검토

### A-22: 일부 구현

서버 저장이 실패하면 오류 문구를 표시하고 입력 화면과 입력값을 유지하며, 성공했을 때만 닫는다. 그러나 IP·포트 형식을 프런트에서 검증하지 않아 `abc` 같은 값은 그대로 서버에 전송된다. 서버가 거부하면 기대대로 동작하지만 서버가 느슨하게 허용하면 잘못된 설정이 저장될 수 있다.

구현 방향: IP 또는 호스트 형식, 포트 범위 1~65535, 필수 계정·경로를 저장 전에 검증하고 필드별 오류를 표시한다.

### A-23: 구현됨

카메라 설정을 정규화해 저장 전후 값을 비교하도록 구현했다. 이름만 변경하거나 모든 설정값이 동일하면 카메라 서버 저장 요청과 `reconnectKey` 증가를 모두 생략한다. ONVIF 포트만 변경된 경우에는 서버에 저장하되 영상 스트림은 유지하고, IP·RTSP 포트·계정·비밀번호·스트림 경로처럼 재생에 영향을 주는 값이 실제로 변경된 경우에만 재연결한다. 비밀번호는 기존 값을 서버에서 받을 수 없으므로 새 값이 입력된 경우에만 변경으로 판정한다.

설정 비교 테스트 7개와 웹·Android APK 빌드가 통과했다. APK를 실기기에 덮어설치하고 카메라 프로필의 입력값 7개를 불러온 뒤 변경 없이 저장했을 때 시트가 정상 종료되고 `/camera` 요청이 0건임을 원격 네트워크 로그로 확인했다. 이후 홈 영상은 `readyState 4`, 재생 상태에서 1.2초 동안 재생 시간이 약 1.21초 증가했고 앱 크래시나 ANR은 없었다.

### A-24: 미구현

SSE의 최신 `infer_raw`는 상태 객체에 저장되지만 홈 화면에서 판정을 표시하지 않는다. 판정의 수신 시각, 만료 시간, 장면 변경 시 초기화 처리도 없다.

구현 방향: 판정과 마지막 수신 시각을 함께 관리하고 홈에 표시한다. 일정 시간 새 판정이 없거나 파이프라인이 정지·오류 상태가 되면 이전 문구를 지우거나 `분석 대기 중`으로 전환한다.

## E. 화면 흐름 전반

### A-25: 일부 구현

홈의 조명·온도·마이크·방향 UI는 조작 가능하다. PTZ만 서버 API에 연결되어 있고, 조명과 온도는 로컬 표시 상태만 변경한다. 마이크는 기기 입력을 분석해 파형을 표시하지만 카메라로 오디오를 송신하지 않는다. `useHomeData`도 현재 실제 API를 호출하지 않는 자리표시자다.

구현 방향: 대응 장치 API가 확정되면 조명·온도·양방향 음성 명령을 연결하고, 지원되지 않는 기능은 UI에 `기기 연동 전` 상태를 명확히 표시한다.

### A-26: 구현됨

일정 추가·수정·삭제, 날짜·시간·하루 종일·반복·알림 선택이 구현되어 있다. 일정은 `localStorage`에 저장되어 재방문과 새로고침 후 유지되며 Android 로컬 알림도 예약·취소된다.

### A-27: 구현됨

알람 설정은 반응형 상태로 관리되고 변경 즉시 `localStorage`에 저장된다. 화면 재진입과 앱 재시작 후 복원된다.

### A-28: 미구현

챗봇 화면과 샘플 대화는 있으나 실제 메시지를 보내면 사용자 메시지만 목록에 추가된다. 코드에 API 연동 예정 주석이 있으며 봇 응답 백엔드는 연결되어 있지 않다.

구현 방향: 챗봇 API 계약을 정하고 대화 ID, 메시지 전송, 응답 스트리밍 또는 폴링, 오류·재시도·로딩 상태를 구현한다. 현재 하드코딩된 샘플 대화는 개발용 fixture로 분리하거나 실제 목록 API로 교체한다.

### A-29: 구현됨

프로필 이름·이미지·견종·생일·검색 기록을 `localStorage`에 저장한다. 테마도 저장하며 루트·body·앱에 라이트/다크 클래스를 적용하고 주요 화면은 공용 팔레트 변수를 사용한다.

이미지 데이터가 브라우저 저장 한도를 넘는 경우와 모든 화면의 시각적 일관성은 수동 검증이 필요하다.

## F. 안드로이드 실기

### A-30: 검증 필요

ADB 연결 기기 `R5CR31E7H5X`에서 디버그 APK 설치와 앱 실행에 성공했고 `MainActivity`가 정상적으로 표시되는 것을 확인했다. 다만 기기에 기존 로그인·서버 데이터가 남아 있어 실행 직후 홈으로 복원되었으므로, 앱 데이터를 삭제해야 확인 가능한 `완전한 첫 실행에서 서버 주소 화면 표시`만 아직 검증하지 못했다. 사용자 저장 데이터를 임의로 삭제하지 않았기 때문에 상태는 `검증 필요`로 유지한다.

### A-31: 검증 필요

실기에서 저장된 세션으로 홈 진입, HLS 영상 재생, WebRTC 전환과 실제 영상 재생, WebRTC에서 HLS UI 전환 기능을 확인했다. WebRTC 전환 후 별도 오류 로그도 발생하지 않았다. 다만 기존 세션을 사용했으므로 A-01·A-02 로그인 절차 자체와 이동통신망의 UDP 8189 연결은 아직 검증하지 못했다. 특히 A-01의 실제 서버 연결 인증은 현재 구현되지 않았으므로 전체 시나리오 상태는 `검증 필요`로 유지한다.

### A-32: 구현됨

ADB로 WebRTC 영상 재생 중 홈 버튼을 눌러 앱을 10초간 백그라운드로 보낸 뒤 다시 실행했다. Android 로그에서 pause와 resume이 확인됐고, 복귀 약 8초 후 WebRTC 실제 영상이 다시 표시됐다. 현재 구현은 `visibilitychange`를 이용하지만 해당 실기 환경에서는 요구 동작을 충족했다.

추가 권장 사항: 더 긴 백그라운드 시간과 화면 잠금에서도 안정성을 높이려면 `@capacitor/app`의 `appStateChange`에서도 동일 복구 함수를 호출하고 중복 재연결을 막는 편이 좋다.

### A-33: 구현됨

브라우저의 `online`·`offline` 네트워크 이벤트를 구독한다. 오프라인이 되면 현재 HLS·WebRTC 연결, 연결 제한 타이머와 A-17 장기 복구 타이머를 정리하고 `네트워크 연결을 확인해주세요.` 상태를 표시한다. 온라인으로 복귀하면 0.5초 동안 네트워크가 안정되기를 기다린 뒤 카메라 설정을 강제로 다시 조회하고 스트림을 새로 연결한다. 이벤트가 연속 발생해도 마지막 이벤트 기준으로 복구 작업을 한 번만 수행한다.

앱이 숨겨진 동안에는 새 연결을 시작하지 않고, 다시 보일 때 온라인 상태이면 즉시 재연결한다. 웹·Android APK 빌드, 실기 덮어설치와 앱 실행을 완료했으며 치명적 실행 오류는 없었다. 실제 Wi-Fi·모바일 데이터 또는 ZeroTier 전환은 사용자 네트워크에 영향을 주므로 자동으로 수행하지 않았고 실기 확인이 필요하다.

### A-34: 구현됨

Android 알림 채널 생성, 권한 요청, SSE 감지 이벤트 감시, 즉시 이상행동 알림, 클립 생성 후 이미지 갱신, 알림 클릭 시 기록 화면 이동이 구현되어 있다.

실기에서 알림 기본 권한이 허용 상태이고 `wally_schedule`, `wally_abnormal` 두 채널이 중요도 3으로 생성된 것을 확인했다. 시스템 알림 목록에 Wally의 `wally_abnormal` 이상행동 알림이 실제 등록된 기록도 확인했다. 이번 점검 중 새로운 행동을 연출하지는 않았으므로 새 감지 순간의 백그라운드 도착 시간은 별도 확인이 필요하다. 앱 프로세스가 중단된 상태까지 보장하려면 서버 푸시 방식이 추가로 필요하다.

### A-35: 구현됨

ADB 강제 회전으로 세로 확대→가로 전체화면→세로 확대를 수행했다. 가로 화면에서 WebRTC 실제 영상과 좌우 컨트롤이 정상 표시됐고 노치·시스템 UI와의 겹침도 발견되지 않았다. 세로로 되돌리면 문서에서 의미하는 원래 배치인 세로 확대 모드로 복원되며 영상도 계속 표시됐다. 해당 상태에서 Android 뒤로가기를 누르면 홈 카드로 정상 복귀한다.

## G. 레이아웃과 반응형

### A-36: 구현됨

`innerWidth > innerHeight`를 기준으로 가로 배치를 전환하고 resize 때 양방향으로 상태를 갱신한다. 데스크톱 웹과 네이티브 앱을 구분하여, 웹에서는 자동 가로 배치에 진입하기 직전의 홈·확대 상태를 저장하고 다시 세로형 비율이 되면 같은 상태로 복원한다. 따라서 홈 카드에서 창을 넓혔다 줄이면 홈 카드로, 세로 확대 상태에서 넓혔다 줄이면 세로 확대 상태로 돌아간다.

Android 앱은 A-35 요구사항에 맞춰 기존의 가로 전체화면→세로 확대 복원 동작을 유지한다. 웹·Android APK 빌드와 실기 덮어설치를 완료했고, 데스크톱 웹에서도 창을 가로형으로 넓혔다가 세로형으로 줄였을 때 기존 홈 배치로 정상 복원되는 것을 사용자 확인으로 검증했다.

### A-37: 구현됨

세로·가로 어느 방향으로 전환하든 열린 PTZ 패드를 닫고 이동 중이면 정지 명령을 전송한다. 조명·온도·말하기·방향 제어 홈 드로어도 실제 화면 비율이 바뀌는 시점에 닫으며, 진행 중인 당겨서 새로고침 동작도 취소한다. 같은 프레임에 `resize`와 `orientationchange`가 함께 발생하면 마지막 요청 하나로 합쳐 레이아웃 상태를 한 번만 갱신하므로 패드나 드로어가 잘못된 위치에 남지 않는다.

웹·Android APK 빌드와 실기 덮어설치를 완료했다. Android 실기기에서 세로 홈 화면의 방향 제어 드로어를 연 뒤 가로로 회전했을 때 드로어가 닫히고 잔존 UI가 없음을 확인했다. 이어 가로 화면에서 PTZ 패드를 연 뒤 세로로 회전했을 때 PTZ 패드가 닫히고 세로 확대 배치로 정상 복원되는 것도 확인했다. 회전을 반복하는 동안 영상 표시와 앱 실행이 유지됐고 요소 겹침이나 치명적 오류가 없었으며, 검증 후 기기의 자동 회전 설정을 원래 값으로 복원했다.

### A-38: 구현됨

가로·세로 판정을 공통 유틸리티로 분리하고 히스테리시스와 120ms debounce를 적용했다. 세로 배치에서는 화면 비율이 1.04 이상일 때만 가로 배치로 진입하고, 가로 배치에서는 0.96 이하일 때만 세로로 복원한다. 그 사이의 정사각형 경계 구간에서는 현재 배치를 유지하므로 몇 픽셀의 반복 변경으로 배치와 영상 요소가 계속 재부착되지 않는다.

경계값 6개에 대한 판정 테스트와 웹·Android APK 빌드가 통과했다. APK를 실기기에 덮어설치하고 세로↔가로 회전을 두 차례 반복했을 때 앱 크래시나 ANR 없이 동작했으며 자동 회전 설정을 원래 값으로 복원했다. 데스크톱 브라우저에서 스트리밍을 재생한 채 정사각형 부근을 직접 미세 드래그하는 최종 육안 확인은 사용자 검증이 필요하다.

### A-39: 구현됨

모바일 브라우저와 네이티브 앱에서는 가변적인 뷰포트 높이 대신 `screen.orientation`의 물리 화면 방향을 우선 사용하도록 공통 방향 판정을 확장했다. 최상위 앱 레이아웃·홈·카메라 화면이 모두 같은 판정을 사용하므로 키보드나 모바일 주소창이 화면 높이만 변경해도 가로 배치로 오인하지 않는다. 데스크톱에서는 A-36·A-38 요구사항대로 창 비율과 완충 구간을 계속 사용한다.

전역 `visualViewport.resize`와 입력 포커스도 감시하여 키보드 크기 변경 후 활성 입력 요소를 보이는 영역으로 맞춘다. 방향 판정 테스트 3개와 웹·Android APK 빌드가 통과했다. APK를 실기기에 덮어설치한 뒤 프로필 이름 입력창에서 화면 키보드를 실제로 띄웠으며, 세로 배치가 유지되고 입력창이 키보드 위에 표시되며 앱 크래시나 ANR이 없음을 확인했다. 모바일 브라우저 주소창 표시·숨김의 최종 확인은 사용자 브라우저 검증이 필요하다.

### A-40: 구현됨

긴 일정 제목과 일정 설정값, 프로필 이름·견종, 설정 메뉴 값처럼 한 줄로 유지해야 하는 정보에는 `min-width: 0`과 말줄임 처리를 적용했다. 챗봇 사용자·봇 메시지, 대화 기록, 행동 로그·장면 설명에는 단어 중간에서도 안전하게 줄바꿈할 수 있도록 `overflow-wrap`과 `word-break`를 적용했다. 이미지·영상·입력 컨트롤의 전역 최대 너비를 제한하고 하단 내비게이션 라벨도 각 탭 영역을 침범하지 않도록 처리했다.

웹·Android APK 빌드와 실기기 덮어설치를 완료했다. Android WebView를 원격 디버깅하여 CSS 폭 360px로 홈·캘린더·챗봇·설정·로그·알람 6개 화면을 순회했고, 각 화면의 기본 상태와 긴 문자열 임시 주입 상태 모두 `documentElement.scrollWidth`와 `body.scrollWidth`가 360px를 유지함을 확인했다. 테스트 문자열은 DOM에만 임시 주입한 뒤 앱 재시작으로 제거했으며 사용자 저장 데이터는 변경하지 않았다. 앱 크래시나 ANR도 발생하지 않았다.

### A-41: 구현됨

공통 로고·시트 헤더, 로그인, 설정 하위 시트, 알람, 행동 로그, 챗봇 헤더·대화 기록 드로어, 하단 내비게이션과 홈 제어 드로어에 상·하단 안전 영역이 반영돼 있다. 가로 카메라 화면은 Android에서 전달하는 컷아웃 좌우 inset과 CSS `safe-area-inset-left/right` 중 큰 값을 사용해 닫기·음소거·새로고침·PTZ·촬영 컨트롤을 안전 영역 안에 배치한다.

연결된 Android 실기기는 상단 중앙 73px 디스플레이 컷아웃과 3버튼 내비게이션을 사용해 시나리오 전제를 충족한다. 홈 세로·가로, 캘린더, 일정 등록 시트, 챗봇, 대화 기록 드로어, 설정 화면을 실제 캡처해 확인했으며 상단 버튼·제목·로고가 컷아웃이나 상태바와 겹치지 않고 하단 입력창·내비게이션·시트 내용이 시스템 내비게이션 영역을 침범하지 않았다. 가로 전체화면의 좌우 카메라 컨트롤도 컷아웃 안전 영역 안에 있었고 앱 크래시나 ANR은 없었다. 검증 후 자동 회전과 홈 화면을 원래 상태로 복원했다.

### A-42: 구현됨

비디오의 실제 `videoWidth/videoHeight`를 읽어 종횡비 CSS 변수로 반영한다. 인라인·확대 영상은 `object-fit: contain`을 사용하고 전환 후 비디오 요소를 다시 붙이므로 원본 비율을 유지하도록 구현되어 있다.

4:3과 16:9 실제 소스의 여백·회전 후 복원은 실기 검증이 필요하다.
